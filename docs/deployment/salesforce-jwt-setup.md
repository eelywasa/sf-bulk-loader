# Salesforce JWT Setup

## What this covers / who should read this

How to configure JWT-based authentication between the Bulk Loader (or the E2E
Tier 2 CI suite) and a Salesforce org. Read this when:

- Connecting the Bulk Loader to a new Salesforce org for production use.
- Setting up the Dev Hub Connected App for E2E Tier 2 CI runs.
- Rotating an expired private key.

This guide covers the **same JWT primitive** in two contexts: production bulk
loads (where the org is a real Salesforce production or sandbox org) and CI
Dev Hub authentication (where the org is the team Dev Hub that provisions
scratch orgs). The steps are identical; only the secrets destination differs.

---

## Background

The Salesforce Bulk API 2.0 requires an authenticated session. The Bulk Loader
uses **JWT Bearer Token** OAuth 2.0 — the server-to-server flow designed for
non-interactive CI/server contexts. There is no browser-redirect step.

Key components:

| Component | What it is |
|-----------|-----------|
| **Connected App** | A Salesforce metadata object that represents the external application. It holds the OAuth consumer key and the certificate used to verify JWT signatures. |
| **Certificate / key pair** | An RSA key pair. The **public key** (as an X.509 certificate) is uploaded to the Connected App. The **private key** stays with the application and signs the JWT assertion at auth time. |
| **Consumer key** | The OAuth client ID generated by Salesforce when you create the Connected App. |
| **Username** | The Salesforce user the JWT will impersonate. This user must be pre-authorised by an admin on the Connected App. |

The same JWT primitive is used by the Bulk Loader in production (`salesforce_auth.py`)
and by the E2E Tier 2 CI workflow (`.github/workflows/e2e-tier-2.yml`). If you
understand one, you understand the other.

## Step 1 — Generate the key pair

Run on any machine with OpenSSL installed (Linux, macOS, WSL):

```bash
# 1a. Generate a 2048-bit RSA private key (PEM format, unencrypted).
openssl genrsa -out server.key 2048

# 1b. Generate a self-signed X.509 certificate from the key.
#     The -days value must exceed your expected key rotation period.
openssl req -new -x509 \
  -key server.key \
  -out server.crt \
  -days 730 \
  -subj "/CN=SFBulkLoaderE2E"
```

You now have two files:

- `server.key` — **private key**. Keep this secret. Never commit it to git.
- `server.crt` — **public certificate**. Safe to share; uploaded to Salesforce.

## Step 2 — Create the External Client App (ECA) in Salesforce

> **Spring '26 constraint**: Salesforce no longer permits creating new
> *Connected Apps* in any org. The replacement is the **External Client App
> (ECA)** — same JWT primitive, newer metadata shape. Existing Connected Apps
> continue to work, but new orgs (including newly-created Dev Hubs and all
> scratch orgs) must use ECAs. The Bulk Loader's E2E suite uses ECAs end-to-end:
> the scratch-org bulk-loader app is deployed via SFDX (see SFBL-324), and the
> Dev Hub CI app is set up via the UI below.

1. Log in to the target Salesforce org (or Dev Hub) as an administrator:
   `sf org open --target-org <alias>`.
2. Go to **Setup → Quick Find: "External Client App" → External Client App
   Manager**.
3. **New External Client App**:
   - **Name**: `SFBulkLoader` (or `SFBulkLoaderDevHubCI` for the Dev Hub).
   - **API Name**: auto-fills; note it.
   - **Contact Email**: your operator email.
   - **Distribution State**: `Local` (NOT `Packaged` — `Packaged` cannot be
     installed in scratch orgs or in the Dev Hub without a managed-package
     pipeline; `Local` works everywhere).
4. Enable **OAuth Settings**:
   - **Callback URL**: `http://localhost:1717/OauthRedirect`
     (the field is required but never used in JWT flow; this is the sf
     CLI's documented default OAuth redirect URI and is what the
     SFDX-deployed bulk-loader ECA also uses — see
     `tests/e2e/sf/sfdx/force-app/main/default/extlClntAppGlobalOauthSets/SfblE2E.ecaGlblOauth-meta.xml`.
     Other plausible values are silently rejected by Salesforce with a
     misleading "INVALID_INPUT: The callback URL provided is not valid"
     error on the *scratch-create* step rather than at ECA save time.
     Specifically, both plain `http://localhost` and
     `https://login.salesforce.com/services/oauth2/success` are rejected
     when the ECA is used as a Dev Hub JWT auth source. Stick with the
     sf CLI default unless you have a specific reason to deviate.)
   - **Selected OAuth Scopes**: add `api`, `refresh_token`, and `offline_access`.
   - **Enable JWT Bearer Flow**: ✓
   - Upload `server.crt` (the public certificate from Step 1).
5. Save. Salesforce generates a **Consumer Key** — note it.
6. After saving, open **Policies → Edit**:
   - Set **IP Relaxation** to *Relax IP Restrictions* (required for CI runners).
   - Set **Permitted Users** to *Admin Pre-Authorized Users*.
7. Pre-authorise the user that will be impersonated by the JWT:
   - Easiest path: add the user's **Profile** to the ECA's permitted profiles
     in the UI.
   - Cleaner path (recommended for the Dev Hub if the org has multiple admins):
     create a Permission Set granting `ExternalClientApplicationAccess` on the
     ECA, then assign that Permission Set to the user **and** link it via a
     `SetupEntityAccess` record. The CI scratch-org flow uses this Permission
     Set + SetupEntityAccess pattern — see
     `tests/e2e/sf/scripts/setup_permset_and_access.sh` for the
     SFDX-deployed example.

> **Note on "Admin Pre-Authorized Users"**: the JWT flow bypasses the OAuth
> consent screen entirely, so the acting user must be pre-authorised on the
> ECA. Any user not in the approved list will receive an `invalid_grant`
> error at auth time.

### Alternative — SFDX deploy of ECA metadata

For reproducible Dev Hub setup (e.g. if you maintain multiple Dev Hubs or want
to version-control the ECA configuration), deploy the same 5-type ECA pattern
SFBL-324 uses for the bulk-loader, with a different `ExternalClientApplication`
name (`SFBulkLoaderDevHubCI`). The metadata files live under a new SFDX
project, and `sf project deploy start --target-org <devhub-alias>` registers
the ECA. The spike report (`tests/e2e/sf/sfdx/SPIKE_REPORT.md`) documents the
metadata shape. Use this path when the UI setup needs to be repeated across
environments.

## Step 3 — Test the JWT flow locally

```bash
# Authenticate to the org:
sf org login jwt \
  -i <CONSUMER_KEY> \
  --jwt-key-file server.key \
  --username <YOUR_SALESFORCE_USERNAME> \
  --instance-url https://login.salesforce.com   # or test.salesforce.com for sandboxes

# Verify you're logged in:
sf org display --target-org <YOUR_SALESFORCE_USERNAME>
```

For Dev Hub authentication (E2E CI), add `--set-default-dev-hub`:

```bash
sf org login jwt \
  -i <DEVHUB_CONSUMER_KEY> \
  --jwt-key-file server.key \
  --username <DEVHUB_USERNAME> \
  --set-default-dev-hub
```

## Step 4 — Store secrets

### Production Bulk Loader (self-hosted or AWS-hosted)

Add the following to `.env` (or the host's secrets manager):

```bash
# The PEM contents of server.key, all on one line with literal \n between lines:
SF_PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----\nMIIEo...\n-----END RSA PRIVATE KEY-----"

# Or store the path to the key file if the app can read it from disk:
# SF_PRIVATE_KEY_FILE=/run/secrets/server.key
```

The Bulk Loader encrypts keys at rest using Fernet (`ENCRYPTION_KEY`). After
storing the key in the UI's **Connections** form, the raw PEM is no longer
accessible from the API — only the encrypted blob is stored.

### E2E Tier 2 CI (GitHub Actions)

The CI Tier 2 workflows use **two** distinct auth flows:

1. **Dev Hub auth** (the outer scratch-org-creation session) → **sfdx-url**, not JWT
2. **Bulk-loader auth into each scratch org** (the inner SF Bulk API session) → **JWT** against the per-scratch ECA deployed by SFBL-324

Add two repository secrets in **Settings → Secrets and variables → Actions**:

| Secret name | Source | Value |
|---|---|---|
| `SFDX_AUTH_URL` | `sf org display --target-org <devhub-alias> --verbose --json \| jq -r '.result.sfdxAuthUrl'` | `force://...` URL encoding a long-lived refresh token for the Dev Hub. |
| `SFBL_E2E_BULK_LOADER_JWT_KEY` | `~/.sfbl-e2e/server.key` (the spike-era keypair's private half) | PEM contents — used inside each scratch org against the SFBL-324-deployed bulk-loader ECA. |

#### Why sfdx-url for Dev Hub auth (not JWT)

PR #89's first Tier 2 wiring used JWT against a Dev Hub ECA. It failed at
scratch-org creation with `RemoteOrgSignupFailed C-1016` — apparently a
Salesforce-side constraint where ECA-authenticated Dev Hub sessions can't
provision scratch orgs. The same failure mode held for UI-created ECAs and
SFDX-deployed ECAs, ruling out metadata shape as the cause.

The sfdx-url path captures the operator's already-working interactive
session (the one that succeeds for `sf org create scratch` locally) and
reproduces it in CI. No ECA needed for Dev Hub access.

#### Generating SFDX_AUTH_URL

1. Authenticate interactively to the Dev Hub on your laptop:
   ```bash
   sf org login web --alias <devhub-alias> --set-default-dev-hub \
     --instance-url https://<yourorg>.my.salesforce.com
   ```
   (Browser opens; click through.)

2. Extract the URL:
   ```bash
   sf org display --target-org <devhub-alias> --verbose --json \
     | jq -r '.result.sfdxAuthUrl'
   ```

3. Store as a GH secret:
   ```bash
   gh secret set SFDX_AUTH_URL --body '<paste the force://... URL>'
   ```

#### Rotation

The sfdx-url contains a long-lived refresh token. Lifetime is
**indefinite-until-revoked** by default; in practice:

| Event | Effect |
|---|---|
| SF admin password change | Refresh token invalidated → URL stops working |
| Manual revoke (Setup → Connected Apps OAuth Usage → Block) | Stops immediately |
| Tightened refresh-token policy on the SF CLI Connected App | New expiry applies |
| Account locked / deactivated | Stops |
| ~30 days of total inactivity (depends on org session policy) | Stops |

Recommended cadence: **rotate annually** as calendar hygiene, or whenever
you change your SF admin password. Re-run the steps under "Generating
SFDX_AUTH_URL" to refresh.

> **Security framing**: unlike JWT (where the GH secret is just the consumer
> key and the private key stays on your laptop), the `SFDX_AUTH_URL` IS the
> full credential. Protect the GH secret like a password. Audit
> Setup → Login History periodically for unexpected IPs.

## Rotating expired keys

1. Generate a new key pair (Step 1).
2. Upload the new `server.crt` to the Connected App (Step 2, "Edit" the app).
3. Update the stored secret (Step 4) with the new `server.key`.
4. Revoke or archive the old key pair.

There is no need to recreate the Connected App — uploading a new certificate
replaces the previous one.

## Org Shape setup (E2E Tier 2 only)

Tier 2 CI can optionally spin up scratch orgs shaped to mirror a production
org's metadata configuration. This is opt-in via the `E2E_ORG_SHAPE` Actions
variable. Before the workflow can use a shaped scratch org, an active org shape
must exist for the source org.

Org Shape creation is **asynchronous and takes ~30 minutes**:

```bash
# Authenticate to the source org (the org whose shape you want to capture):
sf org login jwt -i <CONSUMER_KEY> --jwt-key-file server.key \
  --username <SOURCE_ORG_USERNAME>

# Create the shape (takes ~30 min; use the org's ALIAS, not its ID):
sf org create shape --target-org <source-org-alias>

# Verify the shape is Active before setting E2E_ORG_SHAPE:
sf org list shape --json
```

Once the shape is Active, set the `E2E_ORG_SHAPE` Actions variable
(**Settings → Secrets and variables → Actions → Variables**) to the source
org's 15- or 18-char Salesforce org ID. The CI workflow normalises 18-char
IDs to 15 chars automatically.

> **Important**: `--target-org` on `sf org create shape` takes an **alias**
> (not the raw org ID). `sf org list shape` takes no `--target-org` flag at
> all — it lists all shapes for the authenticated Dev Hub.
